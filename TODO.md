# TODO

Tracking outstanding work that we want to address but haven't scheduled yet. Items are ordered by priority and magnitude of impact within each tier; revisit the ordering whenever a new TODO is added or scope changes.

The deep research initiative has shipped: bounded iterative search, the grounding prerequisite (citation URL lookup and empty-content guardrail), the cross-source connection pass (every connection grounded in at least two cited sources), gap-reason narration streamed as a live research log, and the locations map. It's an opt-in mode layered on the fast 30 second profile, which stays the default front door. Two constraints continue to govern the work: every surfaced connection must rest on cited sources, and per-query cost must stay bounded so the project stays sustainable as usage grows. On the cost front: assessment is folded into the synthesis call (one Sonnet call instead of two, page content sent once), and query normalization folds diacritics, punctuation, and possessives so more spelling variants share one cached result.

With deep research shipped, this pass re-ranks the backlog: several cheap, high-value reach items had drifted into the Low tier below bigger, more speculative work, and abuse protection for the now-live agentic mode had no tracked mitigation. See `docs/vision.md` for the product direction behind these priorities.

## High priority

1. **Act on retained abuse signals (IP blocking).** Anonymous search history keeps query text and IP address forever, on purpose, as an abuse deterrent. But nothing acts on that data yet. Deep research is live now, and it costs noticeably more per query than the fast profile. The only defense today is a daily counter per identity (3 for anonymous users, 20 for signed-in ones), and someone can dodge that by rotating IPs or making throwaway magic-link accounts. Add a way to block or throttle specific IPs or ranges. Check the denylist in the rate-limit path (`store.py`'s `rate:anon:*` Valkey keys are the natural fit), and build it from queries already in `search_history`. Scope must include a way to curate the list, an admin page or a documented command, since a denylist nobody can edit isn't a finished feature.

## Medium priority

Browser SERP backends (Google/Bing via Playwright, or a paid SERP API) remain deferred in the backlog; revisit only if Brave plus Wikipedia coverage falls short.

1. **Per-profile social cards and structured data.** `profile.html` overrides `_base.html`'s Open Graph and Twitter Card block with an empty `{% block social_meta %}{% endblock %}`, so every shared profile link unfurls blank on Slack, iMessage, and social platforms — a direct hit against the product's shareability goal. Populate the block with a title and description built from the query and the existing `/static/og-image.png`, and add `schema.org` `Person`/`Place`/`Event`/`Article` structured data so profiles are eligible for search-engine rich results. Near-zero cost to serve; do this before any dynamic per-profile card image, which depends on the SSE→HTTP hybrid endpoint below.
2. **SSE→HTTP hybrid cacheable result endpoint (scale lever).** Keep SSE for live (cold) runs, so the streaming research-log UX stays. But also add a plain cacheable `GET` that returns the finished profile (JSON or pre-rendered HTML) with `Cache-Control`/`ETag`, populated from the same Valkey cache. The front end tries the fast endpoint first and falls back to SSE on a cold query. Three benefits justify the cost. First, browser and CDN can serve known queries with no server work at all — a latency and scale win on a single, un-autoscaled host. Second, today a crawler sees only an empty "Researching…" SSE shell, so profile content is currently unindexable; this fixes it. Third, it's the prerequisite for a dynamic per-profile social-card image. This is real effort, not a quick win: the cache today stores the raw SSE event list, not a renderable profile, so it needs a design spike before anyone estimates it. It also synergizes with entity canonicalization, since canonical query URLs collapse all aliases to one CDN entry. Alternatives considered: a full SPA plus REST rewrite (the biggest effort, and it changes the whole front end and the streaming UX); a periodic full-page reload with embedded content; and iframes (styling and accessibility cost, so not idiomatic here).
3. **GitHub source link on the results page.** Restore a visible link to the project's GitHub repo so users browsing search results can find the source, read the README, or open issues, a trust signal and a discoverability path for contributors. Place it somewhere unobtrusive (results-page header corner or footer), not the home page. Use the standard GitHub Octocat mark (`fa-brands fa-github`, already loaded sitewide), styled to match the existing theme and small enough that it doesn't compete with the answer. Near-zero cognitive load and zero cost to serve.
4. **IndexNow ping on publish.** Add a tiny background task that posts canonical URLs to the IndexNow endpoint whenever a sitemap-listed page changes (or on deploy). Near-zero effort to gain Bing and Yandex near-instant indexing; Google has not adopted IndexNow so this complements, rather than replaces, sitemap submission.
5. **Print-friendly stylesheet for search results.** Add a print stylesheet to the results page so the profile and sources render cleanly without site chrome. No JavaScript required; this is the baseline shareable format. Keep citations linkable in print.
6. **Evaluate additional public-data search sources.** Investigate which public platforms expose supported APIs we could query to supplement our backends: Twitter/X, Reddit, Hacker News, Stack Exchange, Mastodon, YouTube, GitHub, and the like. For each, capture API availability and stability, auth requirements, rate limits, pricing, terms-of-service constraints on resale/redistribution, and fit with the `SearchBackend` Protocol (`search/base.py`). Output a short ranked recommendation of which to integrate first. This gains importance now that deep research has shipped: more sources means more material for the cross-source connection pass to work with. Sequence before revisiting browser SERP backends below.
7. **Delete account: friendly error when email does not match.** Submitting an email that is not the logged-in user's to the delete account form returns a raw JSON body in the browser instead of a formatted, useful error message. Render the error inline on the account page the same way `routes/auth.py` re-renders `login.html` with an inline error, instead of raising `HTTPException(400)` from `account_delete`. Narrow audience (only users who mistype the email during deletion), which is why this sits behind the reach items above.

## Low priority / backlog

Discretionary features and exploratory research; pick these up when higher tiers are clear or when one becomes strategically interesting.

1. **Entity surfing: "Explore further" section on profile results.** Add a `related_entities` field to `synthesize()` structured output (5–8 named people, organizations, and key events central to the profile) and render it below the profile as a labeled section of links, each opening a new ODIN search in a new tab. Keep entities out of prose to preserve citation clarity; defer inline linking, type badges, and hover previews. A hallucinated entity name is a real search-engine-shaped attack surface: it burns a query slot against the user's daily quota on a garbled search. Include a validation pass on entity names before shipping — reuse the citation-resolution discipline already applied to connections (`_resolve_connection_citations` in `claude.py`) rather than inventing a new approach.
2. **Markdown export for search results.** A downloadable Markdown export from the results page: a dependency-free serialization of `Profile` fields the app already has. Ship this before considering PDF export below.
3. **Recent successful searches on the home page.** Surface a list of recent searches that succeeded on the home page, so visitors get a sense of what the tool can do and what others are finding. The `search_history` table already stores query, category, and timestamp; the remaining work is the home-page surfacing and the display rules. Show query text only, never identifiers. Note: the moderation or allowlist system required to safely display user-supplied queries publicly is at least as much work as the display feature itself — scope both before starting.
4. **PDF export for search results.** Treat as a separate story from Markdown export above: it needs a server-side dependency decision (WeasyPrint or equivalent) with real packaging complexity, Docker image size, and cost-to-serve implications. The print stylesheet plus a browser's built-in print-to-PDF likely covers most of this use case for free — build only on evidence that isn't enough, and only after a dependency spike against the current Docker base image.
5. **Decouple the durable store from the app instance (managed Postgres).** Postgres runs in-stack on the EC2 box (`odin-postgres`). It shares the app's lifecycle and failure domain, and it shares the single 20 GiB EBS volume with Valkey. A single instance or disk failure would lose cache, database, and app together, recoverable only from a daily snapshot. This is a triggered item: promote to Medium on an incident, or on RAM/disk pressure from the shared host. When it moves, provision `db.t4g.micro` in the VPC, add the DSN and credentials to the `odin/app` secret, set `DATABASE_URL` directly, and drop the `odin-postgres` service. RDS automated backups then replace the EBS-snapshot coverage. Roughly +$13/mo on demand, about $8 reserved. Decide together with the migration-owner item below: on RDS, the master user is already not a true Postgres superuser, so part of that item's risk goes away once this ships.
6. **Give database migrations a non-superuser owner.** The app connects as the least-privilege `odin_app` role, but migrations still run as `odin`, the superuser the Postgres image creates. Tighten this by adding a dedicated owner role that can create tables in its schema yet is not a superuser (the `compose/initdb/10-app-role.sh` `NOSUPERUSER` pattern is the template), and reserve the superuser for role creation only. Fold into the managed-Postgres cutover above if that's scheduled soon; otherwise do it standalone, since it's nearly free either way.
7. **Browser SERP backends (Google, Bing, Yahoo) or a paid SERP API.** Revisit only if Brave plus Wikipedia coverage falls short. Cloud-IP dependent and unverifiable from dev; expect the same bot-wall risk that has historically blocked third-party scraping from our IPs. Check host RAM headroom before adding more concurrent Chromium instances — Playwright fetch, Postgres, Valkey, and the app already share a small host. Two paths: (a) Playwright SERP backends that reuse the shared browser and anti-bot setup in `src/odin/fetch.py` (locale, `storage_state`, TLS impersonation), navigate to the engine, and extract organic results into `SearchResult`, tested against saved SERP HTML; or (b) a paid SERP API for Google coverage (for example Serper, Developer plan around $50/yr for 50k queries, 2,500 free/mo). Either way it slots in as a `SearchBackend` via the registry in `src/odin/search/__init__.py`; register browser SERPs as best-effort and let the aggregator drop them silently on a CAPTCHA.
8. **Search-history retention sweep, if volume warrants.** History rows accumulate with no expiry. Anonymous retention is intentional (the abuse deterrent), and signed-in rows already clear on account deletion, so there is no retention need today. Sequence after the IP-blocking item above ships, so a sweep can't delete rows the denylist still needs to consult. If table size becomes a cost or performance problem, add an age-based sweep scoped so it does not undermine the abuse-prevention retention, and update the privacy page if the policy changes.
9. **Backup-restore drill.** Daily snapshots exist, but there's no evidence the restore path has ever been tested end to end. An unverified backup is a hope, not a recovery plan. One-time drill; cheap.
10. **Traversal graph: floating exploration map.** As the user surfs through entity links, build a live force-directed SVG graph in a floating panel (bottom-right corner) showing all traversed nodes (colored by category) and edges (entity → entity navigation). Graph state persists in `localStorage`. The current node pulses; clicking any node reopens its profile. The panel appears once 2+ nodes exist and includes a collapse toggle and clear button. Hard dependency on entity surfing above (nothing to traverse without it). Do not schedule until entity surfing ships and usage data shows people actually traverse more than one hop — the value here is speculative, and the item's own shape (a hand-rolled, stateful, vanilla-JS graph) risks becoming a maintenance burden for a single maintainer if built speculatively. Treat as spike-first: scope the architecture before committing.
